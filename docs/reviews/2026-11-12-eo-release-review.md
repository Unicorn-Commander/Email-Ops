# Email-Ops release review — 2026-11-12

Range: `6258239..origin/main` (`e86eaf9`, PRs #81–#112). Review only; no application code changed.

## Findings

1. **Blocks prod — PLAUSIBLE: an ambiguous send can be repeated after retry.** `backend/src/email/email.service.ts:4447-4484` treats any `callEngine` throw as an unaccepted send, stamps the message `FAILED`, and restores the inbox item to `PENDING`. A concrete input is an approved email whose provider accepts the message but loses the success reply (or whose client throws after delivery). A reviewer can approve the same item again, acquiring the `PENDING` claim and sending a second copy. The new SMTP lane has this exact ambiguity at `backend/src/external-imap/smtp-connection.ts:177-187`: after DATA is submitted, loss of the `250` reply triggers the timeout; `backend/src/external-imap/external-imap.provider.ts:334-351` then reports failure. Each attempt generates a new Message-ID (`backend/src/external-imap/smtp-message.ts:55`), so there is no stable send identity. The existing thrown-engine test confirms the claim is restored (`backend/src/agent-inbox/agent-inbox.approve-sends-once.spec.ts:329-337`); actual acceptance before a lost reply was not reproduced without a transport. This affects any active provider that can deliver and then report an ambiguous failure, even though external IMAP send is flag gated.

2. **Blocks prod — PLAUSIBLE: a crash after the claim can strand an unsent item.** `backend/src/email/email.service.ts:4260-4295` commits `APPROVED/QUEUED` before calling the provider. If the worker exits after that transaction and before `callEngine`, no message leaves. A later approval returns the existing row (`backend/src/email/email.service.ts:3975-3985`), while the due worker selects only `PENDING_APPROVAL` messages (`backend/src/scheduling/scheduling.service.ts:343-353`). There is no recovery path for this concrete state. A post-send status-transaction failure can leave the same visible state, requiring reconciliation before any resend to avoid finding 1.

3. **Fix soon — CONFIRMED: a failed scheduled send stops automatic attempts.** For a due bulk-approved email, `backend/src/email/email.service.ts:4478-4484` records `PENDING/FAILED` after an unaccepted result. `backend/src/scheduling/scheduling.service.ts:343-353` searches only `PENDING_APPROVAL`, so subsequent sweeps never select it. A human can still retry approval; absent that action, it remains failed indefinitely. The following in-memory script executed the real scheduler and printed `FAILED/PENDING scheduled item skipped: PASS`:

```sh
./frontend/node_modules/.bin/tsx -e 'import assert from "node:assert/strict"; import {SchedulingService} from "./backend/src/scheduling/scheduling.service"; const row={id:"item",workspaceId:"workspace-fictional",state:"PENDING",reviewedByUcUid:null,payload:{sends_at:"2026-11-01T00:00:00Z"},message:{status:"FAILED",sendAt:new Date("2026-11-01T00:00:00Z"),mailboxAccountId:"mailbox"}}; let calls=0; const prisma={systemClient:{agentInboxItem:{findMany:async ({where}:any)=>where.state.in.includes(row.state)&&row.message.status===where.message.is.status?[row]:[]}}}; const email={approveAgentInboxItem:async()=>{calls++;return null}}; const service=new SchedulingService(prisma as never,{} as never,{} as never,email as never); service.fireDueAgentInboxSends(new Date("2026-11-12T00:00:00Z")).then((count)=>{assert.equal(count,0);assert.equal(calls,0);console.log("FAILED/PENDING scheduled item skipped: PASS")});'
```

## Requested checks without findings

- **Concurrent single and bulk approval:** Conditional `PENDING → APPROVED` claims (`backend/src/email/email.service.ts:3790-3814,4260-4275`) and the scheduled message-status claim prevent two simultaneous winners in the normal success path. Existing send-once unit tests pass.
- **NOTICE workspace isolation:** Payload IDs only select a client request (`frontend/components/agent-inbox/queue.ts:25-43`). The thread endpoint passes the resolved workspace ID to `listThreadMessagesPage`, and mailbox lookup requires `{ id: mailboxId, workspaceId }` before provider access (`backend/src/mail/mail.controller.ts:343-358`, `backend/src/email/email.service.ts:543-557,683-710`). A foreign workspace mailbox ID cannot resolve to that mailbox. The local open-thread command still uses the same workspace-bound mail API.
- **NOTICE escaping:** Sender, subject, received time, and body render as React text (`frontend/components/agent-inbox/NoticeMessagePreview.tsx:38-59`); HTML body conversion also ends in a text node. A render script with `<img src=x onerror=alert(1)> & text` confirmed escaped markup, not an element:

- **Migrations:** The only two new migrations create `external_imap_accounts`, then add four nullable columns and a CHECK on that new table (`backend/prisma/migrations/20261110193000_external_imap/migration.sql`, `backend/prisma/migrations/20261110210000_external_imap_smtp/migration.sql`). No existing data is deleted or rewritten. The second ALTER takes a table lock, but this table does not exist in the 6258239 production schema; lock exposure is limited to activity on the new table. Prisma tracks application of each migration; the raw SQL is not independently rerunnable.
- **Flags:** External IMAP requires `EXTERNAL_IMAP_ENABLED === 'true'` *and* a workspace allowlist match (`backend/src/external-imap/imap-connection.ts:6-18`); SMTP additionally requires `EXTERNAL_IMAP_SEND_ENABLED === 'true'` (`backend/src/external-imap/smtp-connection.ts:22-25`). All are off when unset. Live production environment values were outside this review fence and were not inspected.
